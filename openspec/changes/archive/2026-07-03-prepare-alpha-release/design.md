# Design — Prepare Alpha Release (1.0.0-alpha)

## Context

The 2026-07-03 release audit found development-phase leftovers that block a public preview: a dead `ApplicationInfo.Version = "0.1.0-boilerplate"` constant, no assembly metadata anywhere, six accrued EF Core migrations scaffolded under EF 9 (the `dotnet-ef` tool is still pinned at 9.0.6 while the packages moved to 10.0.9), user-settings defaults defined independently in `UserSettings` record parameter defaults, `UserSettings.Default`, and hardcoded fallbacks inside `LocalUserSettingsStore.LoadAsync`, plus stale docs and no user-facing documentation. Distribution (publish profiles, CI) is a separate, still-open discussion.

## Goals / Non-Goals

**Goals:**
- One place to bump the version per release; version visible to users and present in logs.
- A single clean `InitialSchema` migration generated by tooling that matches the runtime EF version.
- One authoritative definition of every settings default.
- Docs a fork-and-continue reader or an end user can trust: refreshed technical reference, CHANGELOG, User Guide, NOTICE.

**Non-Goals:**
- Publish profiles, GitHub Actions, release artifacts, code signing, auto-update — deferred to a distribution change.
- Lifting the pre-V1 persistence rule; it stays in force (this change *uses* it for the squash).
- Any settings-format migration/back-compat shims (forbidden pre-V1).

## Decisions

### D1: Version lives in `Directory.Build.props`, code reads it via reflection

A repo-root `Directory.Build.props` sets `<Version>1.0.0-alpha</Version>` plus `Product`, `Authors`, `Copyright`, `RepositoryUrl` for all six projects. `ApplicationInfo.Version` becomes a static property reading `AssemblyInformationalVersionAttribute` from the Application assembly (trimming the `+<commit-hash>` suffix SourceLink appends, if present).

- *Why not keep a const?* Two version sources will drift; the audit found exactly that (`0.1.0-boilerplate` vs manifest `1.0.0.0`).
- *Why the Application assembly, not entry assembly?* All projects get the same version from the shared props file; the Application assembly is reachable from `ApplicationInfo` without Avalonia dependencies, and unit tests exercise it directly.
- `app.manifest` `assemblyIdentity` is hand-synced to `1.0.0.0` → stays numeric-only (manifest versions cannot carry `-alpha`); use `1.0.0.0` and accept it tracks major.minor only.

### D2: Version surfacing — title bar + startup log line

`MainWindowViewModel.Title` returns `$"{ApplicationInfo.Name} {ApplicationInfo.Version}"` (reusing `GetStartupSummary()`, which finally earns its name). On startup, `MainWindow`'s production constructor writes one `IErrorLog.AppendAsync` entry with the startup summary — reusing the existing log port rather than introducing a logging framework.

### D3: Migration squash procedure

1. Bump `dotnet-ef` in `.config/dotnet-tools.json` to `10.0.9`; `dotnet tool restore`.
2. Delete `src/Infrastructure/WF.Reliquary.Infrastructure/Migrations/` entirely (six migrations + snapshot).
3. `dotnet ef migrations add InitialSchema` via the existing `ReliquaryDesignTimeDbContextFactory`.
4. Verify: fresh DB integration tests pass; generated migration contains the merged-view SQL, vault-status objects, and unique indexes previously added incrementally.

- *Why now, when the rule says "squash at V1"?* 1.0-alpha is the first build outsiders run; shipping six dev migrations has no value and the rule's intent ("clean init on the verge of release") applies. The rule text in `docs/technical-reference.md` is amended to record the squash happened at 1.0-alpha and that migrations accrue again until V1 (where a final squash may repeat if any accrued).
- **Consequence:** existing DBs have `__EFMigrationsHistory` rows naming dead migrations; `MigrateAsync` would attempt to re-create existing tables and throw. Pre-V1 rule: no migration shim — CHANGELOG instructs deleting `%LOCALAPPDATA%\WF Reliquary Redux\`.
- Raw SQL previously embedded in migrations (views, seed steps) must be carried into the new `InitialSchema` `Up()`; diff the old migrations' `Sql(...)` calls against the generated file to catch anything the model snapshot cannot express.

### D4: Defaults consolidation — `UserSettings.Default` is the single authority

- Remove default parameter values from the `UserSettings` record positional parameters where they duplicate `Default` (or keep the record parameters but have them sourced from named constants used by `Default` — implementer's choice; the invariant is *one* definition per value).
- `LocalUserSettingsStore.LoadAsync` fallbacks all reference `UserSettings.Default.X` — no enum or numeric literals (`RelicViewMode.Compact`, `RelicsMissionsOrientation.Stacked` are currently hardcoded there).
- New default values: `WindowWidth` 1280, `WindowHeight` 800, `RelicCardWidthPx` 200, `Orientation` SideBySide, and `DropTableSourceDefaults.SourceUrl` = `https://www.warframe.com/droptables`. All other defaults unchanged (FontSizePt 14, ViewMode Compact).
- The new source URL is DE's canonical address; it 302-redirects to the current CDN asset (the old hardcoded URL — verified 2026-07-03). `HttpClient` follows redirects by default (`AllowAutoRedirect`), and the redirect is https→https, so no client change is expected — but the download path must be verified once against the new default. Users who saved the old CDN URL keep it (it still works); no settings rewrite.
- No settings-file changes: absent/invalid fields already fall back, which now picks up the new values automatically.

### D5: Error-log entries carry the version

`FileErrorLog` prefixes each appended entry with the app version alongside the existing timestamp (e.g. `[2026-07-03T12:00:00Z 1.0.0-alpha] ...`). Infrastructure must not reference Presentation, and `ApplicationInfo` lives in Application which Infrastructure already references — read it directly.

### D6: Documentation set

- `CHANGELOG.md` (repo root, Keep-a-Changelog style, single `1.0.0-alpha` section) carries the **data-wipe notice** prominently.
- `docs/user-guide.md` — brief, feature-oriented walkthrough of *non-obvious* behavior: drop-table download vs import being separate steps, wishlist ghost entries surviving re-imports, profiles vs wishlists, Recruiting Chat message template placeholders, relic view modes and the Compact word-clipping rule, owned/vaulted visual separation, appearance window scaling, where data/logs live. Linked from README.
- `NOTICE` (repo root, Apache-2.0 convention): attributions for Caly.Avalonia.Controls.TreeDataGrid fork, Avalonia, CommunityToolkit.Mvvm, AsyncAwaitBestPractices, HtmlAgilityPack, SQLitePCLRaw/SQLite, EF Core; plus a courtesy credit to the original Warframe Reliquary site (wf.xuerian.net) as the inspiration (also already credited in README).
- `docs/technical-reference.md` fixes: EF Core 9 → EF Core 10 (stack table and prose), migrations path `src/Infrastructure/Storage/Migrations/` → `src/Infrastructure/WF.Reliquary.Infrastructure/Migrations/`, drop the "only the one init migration" parenthetical, amend the pre-V1 rule per D3.

## Risks / Trade-offs

- [Squashed migration misses hand-written SQL from intermediate migrations] → explicit diff step in D3.4; integration tests exercise the merged view and vault status against a fresh DB.
- [dotnet-ef 10 scaffolds differently than EF 9 output, producing a large diff] → expected and harmless; the snapshot is regenerated wholesale.
- [Informational version string carries a `+hash` suffix in some build environments] → trim at `+` when reading the attribute.
- [Existing testers launch 1.0-alpha over an old data dir and hit a migration exception] → CHANGELOG notice plus the error toast/log already surface the failure; acceptable pre-V1.
- [1280×800 default exceeds small laptop screens] → Avalonia clamps to the working area on first show; saved size takes over from the second launch.

## Open Questions

- None blocking. Distribution (publish profiles, CI, artifact format) intentionally deferred to a follow-up change.
