## Why

The Presentation layer offloads work to background threads inconsistently, and worse, the offloading that *looks* correct is partly an illusion: the EF Core SQLite provider (`Microsoft.Data.Sqlite`) runs its `…Async` methods **synchronously** on the calling thread, so every `await store.XAsync()` from a ViewModel actually blocks the UI thread for the duration of the query. On top of that, ViewModels fire-and-forget loads and persistence from constructors and property setters with no error surfacing, and only the Drop Tables tab has a busy/cancellation story. The result is latent UI-freeze risk (DB reads, HTML download+parse, and bulk import all run on the UI thread), silent failures when a fire-and-forget task throws, and races when reload chains overlap. This audit establishes a single, uniform concurrency contract — with offloading placed at the data-access seam in Infrastructure rather than scattered across consumers — and brings every ViewModel in line with it before V1.

## What Changes

- **Audit finding — SQLite EF Core calls are not truly async (UI-thread blocking at the data layer).** `Microsoft.Data.Sqlite` executes `ToListAsync`/`SaveChangesAsync`/`ExecuteDeleteAsync`/`SqlQueryRaw(...).ToListAsync` synchronously; awaiting them does not yield the UI thread. Introduce one consistent execution seam **close to the `ReliquaryDbContext`** (a unit-of-work runner in Infrastructure that owns context creation and runs the work on the thread pool), so DB work never runs on the UI thread — applied at the data layer, **not** wrapped per consumer method.
- **Audit finding — non-uniform / wrong-altitude offloading.** `MainWindowViewModel.ReadFromFileAsync` wraps a workflow in `Task.Run`, but `RefreshAsync` (download + synchronous HTML parse) and `ImportAsync` (bulk import) await directly on the UI thread. Make offloading a responsibility of Infrastructure (the data-access seam offloads DB work; the synchronous `HtmlDropTableParser` offloads its own CPU-bound parse) so ViewModels simply `await` and never need to reason about `Task.Run`.
- **Audit finding — unobserved fire-and-forget.** Five ViewModels call `_ = ReloadAsync()`/`_ = LoadAsync()` in constructors, and `PrimePartViewModel.IsChecked` / `PrimeGearCardViewModel.IsOwned` setters call `_ = PersistAsync(...)`. A thrown exception is swallowed with no user feedback. Introduce a shared safe fire-and-forget helper that routes failures to the error-reporting surface (`IErrorReporter`). The surface itself — toast + log file + log-access controls — is delivered by the separate `error-reporting-surface` change; this change only consumes it. Progress/success messages stay in the footer.
- **Audit finding — `async void` command with no error handling.** `AsyncRelayCommand.Execute` is `async void` and does not guard the awaited call; an exception becomes an unhandled exception. Add try/catch with error reporting and a global last-resort handler.
- **Audit finding — no busy state on content tabs.** Only `MainWindowViewModel` exposes `IsBusy`. Prime Gear / Relics / Missions reloads show no progress indication and offer no protection against overlapping reloads. Add a uniform busy/reentrancy guard.
- **Audit finding — overlapping reload chains.** Import, profile-switch, and wishlist-switch callbacks each `await` several `ReloadAsync()` calls that mutate `ObservableCollection`s; a second trigger before the first completes can interleave mutations. Serialize reloads per ViewModel.
- **Audit finding — no `CancellationToken` flow in the UI.** Despite the project convention that all I/O is cancellable, ViewModel methods take no token, so superseded reloads keep running. Thread cancellation through ViewModel operations.
- **Audit finding — blocking `.GetAwaiter().GetResult()` on the UI thread.** `MainWindow`'s constructor and `OnWindowClosing` block on async store calls (wrapped in `Task.Run` to dodge a sync-context deadlock). Document and constrain this to the unavoidable startup/shutdown boundary.
- **Adopt two small, focused packages** instead of hand-rolling all the command/error plumbing: `CommunityToolkit.Mvvm` (replaces `AsyncRelayCommand`/`RelayCommand` and the `INotifyPropertyChanged`/`SetProperty` boilerplate; gives correct `async`-command semantics with `IsRunning` + reentrancy guard for free) and `AsyncAwaitBestPractices` (`SafeFireAndForget` + a global default exception handler for the non-command fire-and-forget cases). The genuinely project-specific pieces — the Infrastructure offload seam and the per-ViewModel reload serialization/cancellation — remain small local helpers.
- Codify all of the above as an explicit, testable UI concurrency contract that future ViewModels must follow.

## Impact

- **Infrastructure (`src/Infrastructure/WF.Reliquary.Infrastructure/`):** a new unit-of-work execution seam in `Storage/` (owns `ReliquaryDbContext` creation + thread-pool offload); every SQLite store/reader (`SqliteWishlistStore`, `SqliteProfileStore`, `SqliteOwnedGearStore`, `SqlitePrimeGearReader`, `SqliteWishlistRelicsReader`, `SqliteWishlistFarmingMissionsReader`, `SqliteImportMetadataReader`, `SqliteDropTableImportStore`, …) routes its context-bound work through it. `IDropTableParser.Parse` becomes async (`ParseAsync`) and `HtmlDropTableParser` offloads its synchronous regex parse — the parse is the heaviest CPU step in the import path and should always have been async (pre-V1, signature change allowed).
- **Presentation (`src/Presentation/WF.Reliquary.Presentation/`):** all ViewModels migrate to `CommunityToolkit.Mvvm` (`[ObservableProperty]`, `[RelayCommand]`/`AsyncRelayCommand`) and stop wrapping store calls in `Task.Run`; constructor/property-setter fire-and-forget routes through `SafeFireAndForget`; failures are routed to `IErrorReporter` (from the `error-reporting-surface` change); content ViewModels gain busy state and a small reload-serialization/cancellation helper; `MainWindow.axaml.cs` startup/shutdown blocking is documented and confined.
- **Dependencies:** add `CommunityToolkit.Mvvm` and `AsyncAwaitBestPractices` (Presentation).
- **Cross-change dependency:** consumes `IErrorReporter` from the `error-reporting-surface` change (built in parallel against the interface; until it lands, failures may route to an interim no-op/footer reporter).
- **Tests:** new unit tests for the contract (DB work runs off the UI thread, failures routed to the reporter, reentrancy guard, cancellation, no `ConfigureAwait(false)` in ViewModels); existing ViewModel/command tests adjusted for the Toolkit command surface.
- **No persistence/schema impact.**
